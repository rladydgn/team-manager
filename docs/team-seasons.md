# 시즌 수정·삭제·메모

## 확정 정책 (2026-11-04, D-F08)

시즌은 이름과 시작일·종료일로 지정하는 통계·순위 필터다. 경기는 시즌 ID에 귀속되지 않는다. 기간을 수정하면 포함되는 경기가 바뀌며 경기·출석·골·도움·클린시트 원본은 변경하지 않는다. 기간은 양끝 날짜를 포함하는 기존 집계 방식을 유지한다.

- 활성 팀장·부팀장이 생성·수정·삭제·기본 지정·정렬한다. 활성 팀원은 목록과 메모를 조회한다. 비로그인·비팀원에게 공개하지 않는다.
- 이름은 앞뒤 공백 제거 후 1~50자, 삭제되지 않은 동일 팀 시즌끼리 대소문자 무시 중복 금지다. 시작일은 종료일 이하여야 한다. 기간 겹침은 허용한다.
- 메모는 선택 입력이며 최대 1,000자 일반 텍스트다. 앞뒤 공백 제거, 빈 메모는 NULL로 저장하고 줄바꿈은 보존한다. HTML은 실행하지 않는다. 생성·수정 화면에서 입력하고 시즌 설정 및 선택한 통계·순위 화면에 표시한다.
- 예: ‘클린시트는 수비수만 집계’, ‘이번 시즌은 수미도 포함’. **메모는 설명이며 실제 집계 코드·포지션 판정·개인 기록을 자동 변경하지 않는다.**
- 삭제는 `deleted_at`을 설정하고 `is_default`를 해제한다. 삭제 시즌은 목록·기본 지정·수정·정렬 대상에서 제외되며 이름 재사용은 가능하다. DB의 원래 이름·기간·메모·등록 정보는 남는다. 복원 UI/API·별도 보관 목록은 제공하지 않는다.
- 기본 시즌 삭제 시 다른 활성 시즌이 있으면 운영진이 대체 기본 시즌을 직접 선택한다. 같은 팀의 다른 활성 시즌만 허용한다. 마지막 시즌은 대체 없이 삭제한다. 일반 시즌 삭제에는 대체를 보내지 않는다.
- 시즌이 없으면 통계·순위의 ‘기간 직접 선택’을 사용한다. 다시 첫 시즌을 생성하면 기본으로 지정된다. 기존 기본 시즌 우선 표시·나머지 순서 변경은 유지한다.

## 화면 흐름

선수 통계 또는 순위의 ‘시즌 설정’에서 각 시즌의 수정/삭제를 선택한다. 수정은 목록 안에서 이름·날짜·메모를 편집한다. 실패하면 입력을 보존한다. 기간 변경 안내를 표시한다. 삭제는 확인 영역에서 기존 기록 보존과 마지막 시즌 여부를 설명하고, 필요한 대체 선택 없이는 확인 버튼을 비활성화한다. 성공한 변경 응답의 전체 목록으로 갱신한다.

통계·순위에서 선택한 시즌의 메모를 줄바꿈 그대로 표시한다. 기간 직접 선택에는 메모를 표시하지 않는다. 목록을 재조회할 때 선택한 시즌이 사라지면 새 기본 시즌 또는 기간 직접 선택으로 전환하고, 선택 시즌 기간이 달라졌으면 집계 기간도 갱신한다. 서버 변경을 실시간 감지하거나 자동 폴링하지는 않는다.

## API

모든 경로는 BE 기준이다. 브라우저에서는 기존 `/api` 접두사를 사용한다. 인증은 기존 HttpOnly 쿠키에서 처리한다. 응답은 `CommonResponse<List<TeamSeasonResponse>>`이며 목록 정렬은 기본 우선 → sortOrder → id다. 각 항목에 `memo: string | null`이 추가된다.

| 메서드·경로 | 용도·입력 |
| --- | --- |
| GET `/teams/{teamId}/seasons` | 활성 팀원 목록 조회 |
| POST `/teams/{teamId}/seasons` | 생성: name, startDate, endDate, memo(생략 가능) |
| PUT `/teams/{teamId}/seasons/{seasonId}` | 이름·기간·메모 전체 수정. memo 생략/null/공백이면 메모 삭제 |
| DELETE `/teams/{teamId}/seasons/{seasonId}?replacementSeasonId={id}` | 기본 삭제 + 다른 시즌이 있을 때만 대체 ID 필수. 나머지 경우 쿼리 생략 |
| PUT `/teams/{teamId}/seasons/{seasonId}/default` | 기존 기본 지정 |
| PUT `/teams/{teamId}/seasons/order` | 기존 전체 활성 시즌 ID 목록 seasonIds로 정렬 |

수정 예:

```json
{
  "name": "2026 후반기",
  "startDate": "2026-07-01",
  "endDate": "2026-12-31",
  "memo": "클린시트는 수비수와 수미 포함\n운영진이 경기 기록 입력 시 확인"
}
```

잘못된 이름·날짜·메모 길이: 400 `INVALID_TEAM_SEASON_REQUEST`. 중복 이름: 409 `DUPLICATE_TEAM_SEASON_NAME`. 대체가 없거나 같은/다른 팀/삭제 시즌 또는 불필요한 대체: 409 `INVALID_TEAM_SEASON_REPLACEMENT`. 존재하지 않거나 다른 팀·삭제 시즌: 404 `TEAM_SEASON_NOT_FOUND`. 비운영진 쓰기: 내부 403 오류이며 기존 GlobalExceptionHandler의 접근 은닉 정책으로 HTTP 404 응답. 기존 인증·활성 팀·팀원 검사 유지.

모든 시즌 쓰기는 같은 팀 행을 FOR UPDATE로 잠근 뒤 활성 시즌도 current read로 읽는다. 생성·기본 지정·수정·삭제·정렬이 같은 잠금을 사용한다. 대체 지정과 삭제는 하나의 Spring 트랜잭션이다. 이번 범위는 기본 시즌 일관성이며 편집 내용의 버전 비교·상세 변경 이력(T01)은 추가하지 않았다. 같은 시즌을 연속 수정하면 나중에 저장한 내용이 적용된다.

## DB 변경과 다음 세션

새 컬럼은 `team_seasons.memo VARCHAR(1000) NULL` 하나다. 기존 deleted_at/is_default/updated_at을 활용한다. 신규 설치 정의는 `be/src/main/resources/schema.sql`, 기존 DB용 DDL은 **누적 change_schema.sql 끝의 `Season memo (2026-11-04)` 블록**이다. 컬럼이 없는 DB에 해당 블록만 한 번 적용한다. 이미 있다면 건너뛴다. 누적 파일 전체를 재실행하지 않는다. 실제 DB에 자동 적용하는 설정은 추가하지 않았다.

기존 행의 메모는 NULL이며 기존 이름·기간·기본·순서는 보존된다. 본 변경은 실제 DB 적용·운영 접속·배포를 수행하지 않는다. 컬럼을 적용하기 전 새 ORM 코드를 연결하면 조회가 실패하므로 적용 여부는 별도 확인이 필요하다.

BE 구현은 TeamSeasonController → TeamSeasonService → TeamSeasonRepository 및 TeamSeasonsTable/Entity/Record/DTO다. FE는 `features/team/api/season.ts`, `app/team/[teamId]/season`과 통계·순위 페이지다. 후속 세션은 이 문서와 작업 계획의 마지막 F08 결과부터 읽고 D-F08을 다시 묻지 않는다. 메모를 자동 집계 정책으로 해석하거나 복원 기능을 임의로 추가하지 않는다.

검증 결과와 미실행 범위는 [작업 계획](project-improvement-work-plan.md)의 2026-11-04 F08 기록을 따른다. 실제 MySQL의 잠금·DDL 검증은 H2 결과와 구분한다.
