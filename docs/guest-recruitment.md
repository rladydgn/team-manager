# 커뮤니티 · 용병 모집 기획 초안

작성일: 2026-11-04. 상태: **문서 초안 / 제품 결정·DB 설계 미승인 / 구현 전**.

이번 요청은 문서 작성이다. 아래 권장안·화면·API·테이블은 검토안이며 구현 승인이 아니다. 사용자 답변 없이 API·화면·스키마를 변경하지 않는다. 기존 개선 ID와 별도로 **C01 용병 모집**으로 관리한다. 전체 커뮤니티를 한 번에 만들지 않는다.

## 1. 사용자가 요청한 핵심

1. 용병 모집 페이지에서 사용자가 팀과 경기를 선택해 모집글을 작성한다.
2. 다른 사용자가 모집글에 신청한다.
3. 작성자가 신청을 확인하고 승인하면 신청자를 용병으로 자동 등록해 해당 경기 명단에 포함한다.

‘확인’은 단순 열람과 구분해 **명시적인 승인 버튼**으로 표현하는 안을 제안한다. 상세를 보기만 했는데 승인되는 동작은 피한다. 어떤 사용자가 어느 팀으로 글을 쓸 수 있는지, 승인 후 팀 소속·조회 권한, 취소·마감·공개 범위는 아직 확정되지 않았다.

## 2. 처음 제공할 범위 제안

모집 목록·상세·작성/수정/마감, 신청·본인 신청 목록·승인 전 철회, 작성자의 신청자 확인·승인/거절, 승인 후 경기 명단 연결을 하나의 흐름으로 제공한다. 승인 결과는 내 신청 목록에서 확인한다. 제목/경기일 기준 목록 필터와 페이지네이션을 제공하는 안이다.

자유게시판·댓글·좋아요·실시간 채팅·결제/환불·평점·외부 문자/메일/푸시·이미지 첨부는 첫 범위에서 제외하는 안이다. 필요한 경우 별도 요청/결정으로 추가한다. 모집글에 비용 안내를 적는 기능과 실제 돈을 결제하는 기능은 구분한다. 외부 알림 없이도 신청자가 승인/거절 상태를 직접 확인할 수 있어야 한다.

## 4. 화면과 사용자 흐름 제안

### 모집글 작성

로그인 → ‘용병 모집’ → ‘모집글 작성’ → 권한 있는 팀 선택 → 해당 팀의 예정 경기 선택 → 제목·모집 인원·모집 종료 시각·모집 포지션(선택)·안내문 입력 → 공개 정보 미리보기 → 등록.

팀·경기 선택은 서버에서 권한과 소속 관계를 다시 검증한다. 경기의 날짜/시각·장소는 연결된 경기에서 가져오고 글마다 별도 사실처럼 입력하지 않는다. 승인자가 생기거나 신청이 들어온 뒤에는 글을 다른 팀/경기에 바꾸지 않고 새 글을 작성하는 안이다. 날짜는 Asia/Seoul 기준으로 명시한다.

작성 폼에는 ‘이 정보는 외부 사용자에게 공개됩니다’와 실제 공개할 경기 정보만 미리 보여준다. 기존 팀 전용 메모를 자동 복사하지 않는다. 장소 공개 범위·비용 입력 방식·포지션별 정원은 미결정이다.

### 신청자

목록 → 상세에서 경기/모집 조건 확인 → 로그인 후 ‘신청하기’ → 희망 포지션·짧은 신청 메모 입력 → 내 신청에서 ‘승인 대기’ 확인 → 작성자 승인 시 ‘참가 확정’과 해당 경기용 안내 확인.

신청 버튼 옆에 ‘작성자 승인 후 참가가 확정됩니다’를 표시한다. 이미 신청했으면 새 신청 대신 기존 상태를 표시한다. 승인 대기 상태는 본인이 철회할 수 있는 안이다. 승인 후 취소는 별도 정책이며 승인 전 철회와 같은 삭제 API로 처리하지 않는다. 연락처·전체 생년월일·이메일을 자동 공개하지 않는다.

### 작성자

내 모집글 → 신청자 목록(대기/승인/거절/철회 구분) → 신청 내용 확인 → ‘승인’ 또는 ‘거절’ → 승인 확인에 경기·선수·남은 정원을 표시 → 승인 완료 후 연결된 경기 명단 확인.

경기 상세의 일반 명단에는 용병 이름과 모집으로 확정된 참가자임을 구분할 수 있어야 한다. 신청 메모·심사 이력은 일반 경기 응답에 섞어 공개하지 않는다. 자체전 승인 선수는 편 미배정 안내 후 운영진이 편을 지정한다. 포메이션에 자동 배치하지 않는다.

### 화면 진입점과 반응형

전역 ‘커뮤니티 > 용병 모집’, 경기 운영진 영역의 ‘용병 모집글 작성’, 본인의 ‘내 신청’, 작성자의 ‘내 모집글’을 제안한다. 메뉴명·노출은 구현 전에 기존 내비게이션과 함께 확정한다. 모바일은 경기 정보 카드와 신청/승인 버튼을 세로로 배치하고, 데스크톱은 목록과 상세의 정보 순서를 유지한다. 상태는 색상과 텍스트를 함께 사용하며 실패한 폼 입력은 보존한다.

## 6. 상태와 처리 규칙 초안

모집글 저장 상태는 OPEN(모집), CLOSED(작성자 마감), CANCELED(모집 취소)를 후보로 둔다. 인원 충족(FULL), 기간 만료(EXPIRED), 경기 무효는 승인 수·현재 시각·경기 상태로 계산하는 유효 상태로 구분한다. 따라서 배치 작업이 없어도 마감 시각이 지나면 신청을 차단한다. 수동 마감과 단순 만료를 같은 상태로 덮어쓰지 않는다. 인원 충족/만료·수동 마감의 표시 우선순위와 재개방 정책은 D-C01-LIMIT/TIME/CANCEL에서 확정한다.

신청 상태 후보는 PENDING → APPROVED / REJECTED / WITHDRAWN이다. 승인 후 취소가 합의되면 APPROVED → CANCEL_REQUESTED → CANCELED 또는 APPROVED 복귀를 추가한다. 거절/철회 후 재신청 여부와 기존 행 재사용 여부는 미확정이다. 승인 상태를 제외한 단순 열람은 상태를 바꾸지 않는다. 승인 수는 유효하게 확정된 신청을 세며 취소 요청 중에는 자리와 경기 참가를 유지하는 안이다.

모집글 삭제/취소와 경기 취소는 다르다. 모집글을 숨겼다는 이유만으로 확정 참가자·기록을 삭제하지 않는다. 경기 취소 시 글은 신청 불가로 보이고 신청자에게 경기 취소 상태를 안내한다. 기존 확정의 감사 이력과 경기 원본은 보존한다. 재개 시 신청 자동 복구·재승인을 할지는 정책 확정 전 구현하지 않는다. F04 일정 변경/취소 전체 기능을 이번 기능의 선행 완료로 가정하지 않으며, 이미 저장 가능한 CANCELED/COMPLETED 상태를 최소한 재검증한다.

승인 시 다음 사항을 **하나의 트랜잭션**에서 처리하는 안이다.

1. 로그인 사용자·현재 작성/승인 권한·활성 팀·경기의 팀 일치를 검증한다.
2. 경기와 모집글을 잠그고 유효 상태·경기 시작/기록 유무·정원·신청 상태를 최신 데이터로 재검증한다.
3. 신청자 계정을 확인하고 기존 팀원·기존 참가자를 계정 ID 기준으로 조회한다. 이름만으로 선수/비회원을 연결하지 않는다.
4. 확정된 소속 모델에 따라 해당 경기용 참가 신원을 연결하거나 용병 팀원을 생성/재사용한다. 기존 LEFT/PENDING/동명이인 비회원은 자동 재가입/승격/연결하지 않는다.
5. 해당 경기 참가자를 한 번만 생성/연결하고, **참석 예정 AVAILABLE로 연결하는 안**을 적용한다. 기존 불참 응답은 승인 동의 범위와 충돌하므로 명시적 처리 정책을 결정한다. 다른 경기 참가자는 변경하지 않는다.
6. 신청 APPROVED·처리자·시각·참가자 연결 및 상태 전이 이력을 함께 저장한다. 모두 성공했을 때만 확정 응답을 반환한다.

실제 출석=false, 지각=false, 골/도움/클린시트=0을 초기값으로 유지한다. 외부전은 기존 HOME, 자체전은 UNASSIGNED로 시작하는 안이다. 기존 편/기록이 있는 참가자를 재사용할 때 이 필드를 초기화하지 않는다. API 응답 유실 후 재시도는 이미 연결된 동일 승인 결과를 반환하며 선수·신청·정원 카운트를 중복 생성하지 않아야 한다.

기존 경기 기록 저장·편 배정과 잠금 순서를 맞춘다. 모집 서비스의 팀/경기/글/신청 잠금 순서는 구현 조사 후 한 가지로 명시하고 기존 팀원 추가·탈퇴·경기 기록 서비스의 순서와 충돌하지 않게 한다. UNIQUE 키 없이 중복 신청은 같은 글 잠금, 동일 경기 참가자는 경기 잠금, 팀 용병 생성이 필요하면 같은 팀/계정에 대한 공통 직렬화 전략으로 보장한다. 단순 조회 후 INSERT만으로 경쟁을 막았다고 간주하지 않는다.

## 7. 데이터 모델 검토안 — SQL 아님

### 공통 테이블 후보

| 테이블 | 주요 컬럼 후보 | 목적 |
| --- | --- | --- |
| guest_recruitment_posts | id, team_id, match_id, created_by_user_id, title(100), content(TEXT·입력 상한 제안 5,000자), capacity, recruitment_deadline_at, status, version, created_at, updated_at, deleted_at | 팀/경기 연결·모집 조건·수정 충돌 판정 |
| guest_recruitment_applications | id, recruitment_post_id, applicant_user_id, requested_position(nullable), message(nullable·500자 제안), status, version, reviewed_by_user_id(nullable), reviewed_at(nullable), approved_match_participant_id(nullable), created_at, updated_at | 신청 계정·현재 심사 상태·승인 결과 연결 |
| guest_recruitment_application_events | id, application_id, actor_user_id(nullable), from_status(nullable), to_status, reason(nullable), created_at | 신청/승인/철회/취소 및 재시도 판단에 필요한 전이 이력. 자동 처리 actor NULL 의미를 별도 정의 |

이름은 아직 후보이며 enum/문자열 길이·nullable·재신청 모델·삭제/보존 기간은 확정 전이다. 인덱스 후보는 글(team_id, match_id, deleted_at), (status, recruitment_deadline_at, id), 신청(recruitment_post_id, status, id), (applicant_user_id, created_at, id), 이력(application_id, id)다. PK 외 UNIQUE/FK/CHECK 제약은 추가하지 않는 프로젝트 규칙을 따른다. 정원·시간·중복·참조 일치는 서비스에서 검증한다.

### 용병 신원과 경기 참가 연결 — D-C01-MEMBERSHIP 이후 설계

- **팀 용병 계속 등록 선택:** 기존 team_members에 applicant_user_id가 연결된 GUEST를 생성/재사용하고 match_participants.team_member_id를 연결할 수 있다. 단, 일반 등록의 다른 경기 자동 추가를 호출하지 않는다. 계정이 이미 MEMBER/OWNER/SUB_MANAGER인 경우 역할을 GUEST로 덮어쓰지 않는다. 팀 전체 열람 및 회원/회비/통계에 포함되는 효과를 사용자에게 알린다.
- **해당 경기 한정 선택:** 현 스키마에 없는 경기 한정 자격을 추가해야 한다. 별도 경기 용병 신원+참가자 식별 확장 또는 명시적인 소속 범위를 가진 팀원 모델을 비교 설계한다. GUEST 행을 만들고 UI만 숨기는 것은 경기 한정 권한 구현이 아니다. `team_member_id`의 null 허용 하나만 바꿔도 명단/포메이션/통계가 자동 지원되지 않는다.
- 어느 쪽이든 승인 결과는 applicant_user_id → 참가 신원 → match_participant로 추적 가능해야 하며 비회원 선수와 이름만으로 연결하지 않는다. 기존 참가자 생성·투표·명단 제외·내보내기·계정 연결과의 중복을 검증해야 한다.

따라서 **위 공통 테이블만으로 경기 한정 모델이 완성됐다고 간주하지 않는다.** 이 결정 후 참가자·권한·포메이션·통계의 변경안까지 함께 작성해 DB 구조를 검토받고, 구현 시 신규 schema.sql과 change_schema.sql 끝에 승인된 DDL만 추가한다. 이번 문서 작업에서는 SQL 파일을 변경하지 않는다.

## 8. API 초안

BE 경로 후보이며 전부 미구현이다. 브라우저는 기존 `/api` 접두사를 사용한다. 기존 CommonResponse·HttpOnly 쿠키·서버 사용자 식별을 재사용하며 body의 신청자/승인자 userId를 신뢰하지 않는다.

| 경로 후보 | 동작 |
| --- | --- |
| GET `/guest-recruitments` | 공개 범위에 맞춘 목록·검색·페이지네이션. 신청자/내부 팀 메모 제외 |
| GET `/guest-recruitments/{postId}` | 공개 상세와 권한 있는 사용자에게만 본인 신청/관리 가능 여부 |
| POST `/guest-recruitments` | teamId, matchId, title, content, capacity, recruitmentDeadlineAt 등으로 등록 |
| PUT `/guest-recruitments/{postId}` | version을 포함한 글 수정. 승인 수 이하 정원 축소 등 거절 |
| PUT `/guest-recruitments/{postId}/status` | 마감/취소 및 합의된 재개방. version 필수 |
| POST `/guest-recruitments/{postId}/applications` | 로그인 본인 신청, 희망 포지션·메모 |
| GET `/guest-recruitments/{postId}/applications` | 작성자/합의된 담당 운영진의 심사 목록 |
| PUT `/guest-recruitment-applications/{id}/withdraw` | 본인 승인 전 철회, version 필수 |
| PUT `/guest-recruitment-applications/{id}/review` | APPROVE/REJECT, version 포함, 승인과 경기 편입 원자 처리 |
| GET `/users/me/guest-applications` | 본인 신청·심사 결과·참여 경기 안내 |
| GET `/users/me/guest-recruitments` | 본인이 작성한 모집글 |

승인 후 취소 요청/처리, 경기 한정 참가자 안내 API는 관련 결정 이후 추가한다. 기존 `GET /matches/{id}`의 팀원 검사를 무조건 해제하지 않는다. 공개 모집 상세는 기존 MatchResponse를 그대로 재사용하지 않고 공개 필드 전용 DTO를 사용한다.

오류 구분안: 입력/참조 불일치 400, 인증 401, 조회 불가 404(기존 접근 은닉 준수), 정원 초과·마감·버전/상태 충돌·이미 참가 중 409. 재시도 가능한 서버 오류 5xx는 입력을 보존한다. 동일 승인 재요청은 중복 처리 없이 같은 결과, 이미 거절/철회된 신청의 승인은 409로 구분하는 안이다. 정확한 오류 코드·응답은 구현 전 API 계약에서 확정한다.

## 9. 검증할 시나리오와 완료 기준

- 운영진/일반 팀원/비팀원·권한 상실 작성자, 다른 팀 경기 ID, 삭제 팀·경기·모집글의 서버 권한 검사.
- 비로그인 공개 목록/상세의 허용 필드만 노출. 신청자·심사 메모·계정 이메일·팀 내부 메모 비노출. 다른 신청자의 ID를 바꾼 조회/철회/승인 차단.
- 신청 중복 클릭·동시 요청·다른 글에서 같은 경기 신청·기존 계정 연결 용병·동명이인 비회원·LEFT/PENDING 멤버의 중복/자동 승격 방지.
- 정원 마지막 한 자리를 두 명이 동시 승인, 같은 신청을 두 운영자가 승인/거절, 응답 유실 재시도에서 참가자와 정원 정확성.
- 승인 직전 글 마감/경기 취소/기록 저장/시작 시각/모집 종료 시각 변경, 경계 시각의 Asia/Seoul 판정. 승인 실패 시 일부 참가자만 생기지 않음.
- 승인 용병이 해당 경기에 한 번 포함됨. AVAILABLE·자체전 편 배정 후 포메이션 후보 연계, 실제 출석·개인 기록·기존 편/기록 미변경.
- 승인 취소·모집 취소·탈퇴 시 기존 경기 출석·기록·편·포메이션 보존 정책을 준수. 기존 F03/F10/F02 보호 회귀.
- 경기 한정 방식이면 다른 경기/팀원 목록/통계·회비 접근과 다른 경기 자동 참가가 없음. 팀 소속 방식이면 승인받은 범위에서만 포함됨.
- 모바일 375px·데스크톱 1440px에서 작성·신청·승인·실패 재시도·빈 목록·마감·정원 충족·취소 표시 확인. 필수 동작만 최소 자동 테스트 작성.
- 신규/기존 DDL을 격리 DB에서 검증하고 H2와 실제 MySQL 결과를 구분한다. 문서·린트·타입·관련 테스트 결과를 실행 단위별로 기록한다.

완료는 모집글을 저장하는 것만이 아니라, ‘신청자 신청 → 작성자 승인 → 단 한 번 경기 편입 → 신청자 결과 확인’이 권한/정원/기록 보호와 함께 연결되는 상태다. 현재는 어떤 시나리오도 구현·실행 완료가 아니다.

## 10. 구현 순서와 다음 세션 시작점

1. 이 문서와 [작업 계획](project-improvement-work-plan.md)의 C01 기록을 읽는다. 사용자 요청에서 확정된 핵심 흐름과 미결정 정책을 구분한다.
2. AUTH·MEMBERSHIP·PUBLIC 확인 후 LIMIT·TIME·CANCEL을 최대 3개씩 묻는다. 경기 한정 모델 선택 시 기존 권한·참가자/포메이션/통계 영향 분석과 테이블/전환안을 먼저 제시한다.
3. 승인된 DB 구조·상태 전이·API 공개 DTO·잠금 순서를 구체화하고 원본 기록 보존/기존 용병 호환 경로를 정한다. 미확정 항목에 의존하는 구현은 기다린다.
4. 서버 모델·조회/작성 → 신청/심사·트랜잭션 연결 → FE 목록/상세·내 신청·관리 → 반응형·회귀 검증 순으로 진행한다. 기능이 끝까지 연결되기 전 전체 완료로 기록하지 않는다.
5. 결정·DDL/API·검증·남은 항목을 이 문서와 작업 계획에 반영하고 완료 작업 단위별로 상세 메시지를 남겨 커밋한다. 실제 DB 적용·배포·서버 설정·푸시는 별도 지시 없이 수행하지 않는다.

기존 N04 전체 알림·F04 전체 일정 수정·T01 전체 감사 기능을 이 요청으로 승인받은 것으로 해석하지 않는다. 제거된 F01도 복구하지 않는다. 실제 코드/DDL/화면을 만들라는 지시를 받기 전에는 문서 검토 상태를 유지한다.
