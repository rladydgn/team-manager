# Team Manager 프로젝트 점검과 기능 개선 제안

작성일: 2026-10-19 · 재검토일: 2026-10-23 · 코드 기준: `ef50a75` 작업 트리의 프런트엔드·백엔드·DB 정의·배포 설정

주요 팀 운영 기능은 이미 갖춰져 있다. 다음 단계에서는 **과거 경기 명단·기록 보호, 삭제된 팀의 경기 접근 차단, 비회원 참석 처리, 자체 경기 점수와 실제 출석의 일관성**을 먼저 보완하고, 일정 변경·취소와 운영진 업무 요약을 연결하는 것이 효과적이다.

이 문서는 개발 후보를 정리한 제안서다. 확인한 코드 동작, 운영 정책을 정해야 하는 사항, 신규 기능을 구분했다. 운영 DB·실제 배포 환경·브라우저 동작·동시 요청은 검증하지 않았다. 2026-10-23 재검토에서는 프런트 기본 테스트 11개와 기본 실행에서 빠진 메모 테스트 4개를 실행해 모두 통과했다. 이 테스트들은 아래 서버 문제를 재현하는 테스트가 아니며, 백엔드 테스트의 현재 통과 여부도 이번 검토로 확인한 것은 아니다.

### 재검토 결과

기존 문서는 F01~F09, N01~N09, T01~T04의 22개 항목과 진행 순서까지 작성되어 있었다. 문장이 중간에 끊기거나 항목이 비어 있는 상태는 아니며, 주요 지적의 코드 근거도 유지된다. 다만 전체 프로젝트의 모든 경로를 검증한 문서로 볼 수는 없어 다음을 보완했다.

- **누락 추가:** 과거 명단 편집 시 기존 참가자·점수 불일치(F10), 삭제된 팀의 경기 API 접근 검사(F11), 계정 복구에 필요한 서버 세션 폐기(T05).
- **구체화:** 취소 경기의 과거 명단 수정 경로, 출석 지표의 수치 예시, 통계 전체 정렬을 유지하는 페이지 처리, 기존 UNIQUE 제약과 신규 제약 지침의 차이.
- **검증 근거 보강:** 8절에 기존 항목의 재검토 결과와 실행 범위, 9절에 우선 항목별 재현·인수 시나리오를 기록했다. 해당 시나리오는 앞으로 실행할 검증 기준이며 통과 결과가 아니다.

총 25개 제안의 제품 검토·개발 우선순위 문서로 활용할 수 있다. 개별 작업 착수 시 API 계약, 데이터 전환 및 회귀 테스트를 추가로 확정해야 한다.

실행 순서·완료 조건·착수 시 질문할 결정 사항은 [개선 작업 계획](project-improvement-work-plan.md)에 정리했다. 미결정 정책은 해당 작업에서 사용자에게 확인한 뒤 구현하고, 권장안을 확정 요구사항으로 간주하지 않는다.

## 3. 기존 기능에서 수정·보완할 사항

### F01. 비회원·용병의 예정 경기 참석 등록

**현재:** `updateMatchParticipation()`은 로그인 사용자의 팀원 ID만 수정한다. 신규 경기 참가자는 `PENDING`으로 생성되고, 운영진의 명단 편집은 경기 시각이 지난 뒤 사용하는 과거 경기 API에 있다. 포메이션은 `AVAILABLE`인 선수만 배치한다.

**영향:** 계정이 없는 선수는 예정 경기에서 직접 투표할 수 없고, 운영진이 참석으로 바꾸는 일반 UI/API도 확인되지 않는다. 등록해 둔 용병을 경기 전에 후보·포메이션에 넣는 흐름이 막힌다.

**제안:** 운영진 전용으로 경기 참가 명단과 참석 상태를 수정한다. 본인 응답과 대리 등록을 구분해 변경자·시각을 남기고, 마감 후 정정 가능 범위를 명시한다. 비회원 등록 자체는 기존 기능을 재사용한다.

**완료 기준:** 계정 없는 팀원을 참석 등록하면 후보에 나타난다. 일반 팀원은 타인의 상태를 바꿀 수 없다. 불참 정정 시 기존 포메이션은 현재의 배치 제외 정책을 따른다.

근거: [MatchService.kt](../be/src/main/kotlin/com/yonghoo/team_manager/match/service/MatchService.kt)의 `updateMatchParticipation`, `updateHistoricalMatchParticipants`; [MatchParticipantRepository.kt](../be/src/main/kotlin/com/yonghoo/team_manager/match/repository/MatchParticipantRepository.kt)의 `createDefaultParticipants`; [MatchFormationService.kt](../be/src/main/kotlin/com/yonghoo/team_manager/match/service/MatchFormationService.kt)의 `attending`.

### F02. 자체 경기 점수를 홈·어웨이별로 계산

**현재:** 자체 경기의 편 배정은 저장하지만, 기록 저장은 편과 관계없이 모든 참가자의 골을 더해 `teamScore`로 만든다. 프런트엔드도 모든 선수의 골 합계를 우리 팀 점수로 표시하고 상대 점수는 별도로 입력한다.

**영향:** 홈 선수 2골·어웨이 선수 1골을 기록하면 선수 골 합계 3이 우리 팀 점수가 된다. 편별 기록과 경기 점수를 함께 관리하기 어렵다.

**제안:** 외부 경기는 현재 우리 팀·상대 팀 방식을 유지하고, 자체 경기는 HOME/AWAY별 득점과 미지정 득점을 분리한다. 편이 없는 득점 선수의 처리, 기록 확정 후 편 변경, 자체 경기의 승·무·패 표시 정책도 함께 정한다.

**완료 기준:** 홈 2골·어웨이 1골 사례에서 2:1로 일치한다. 양쪽 어시스트 검증은 각 편의 득점에 적용된다. 기존 자체 경기 데이터는 임의로 재계산하지 않고 확인이 필요한 대상으로 안내한다.

근거: [MatchService.kt](../be/src/main/kotlin/com/yonghoo/team_manager/match/service/MatchService.kt)의 `updateMatchRecord`, `validateMatchRecordRequest`; [기록 화면](../fe/src/app/match/[matchId]/record/page.tsx)의 `teamScore`; [MatchRecordUpdateRequest.kt](../be/src/main/kotlin/com/yonghoo/team_manager/match/dto/MatchRecordUpdateRequest.kt).

### F03. 불참 상태와 개인 기록이 서로 바뀌지 않도록 검증

**현재:** 실제 참여 체크를 해제해도 골·어시스트·클린시트 값은 남는다. 서버는 불참자의 지각은 거절하지만, 불참자의 양수 개인 기록은 거절하지 않는다. 다시 편집 화면을 열면 개인 기록이 하나라도 있다는 이유로 실제 참여를 참으로 표시한다.

**영향:** 같은 선수에게 불참과 득점이 동시에 저장될 수 있다. 다음 저장에서 운영진이 출석을 수정하지 않았는데도 실제 참여가 참으로 바뀌어 출석률과 투표 후 불참 횟수가 달라질 수 있다.

**제안:** 불참 처리 시 남아 있는 기록을 알리고 사용자가 정정하게 한다. 서버에서도 동일한 규칙을 검증한다. 조회 시 출석 상태를 묵시적으로 보정하는 코드는 제거하고, 기존 모순 데이터는 별도 점검 대상으로 표시한다.

**완료 기준:** 불참+골 1 같은 요청은 명확한 오류로 거절된다. 출석·기록을 수정하지 않고 조회 후 저장해도 출석이 바뀌지 않는다. 정상 불참 기록은 최근 적용한 출석률 제외 규칙과 일치한다.

근거: [기록 화면](../fe/src/app/match/[matchId]/record/page.tsx)의 `updatePlayerParticipation`, `hasRecordedStatistics`; [MatchService.kt](../be/src/main/kotlin/com/yonghoo/team_manager/match/service/MatchService.kt)의 `validateMatchRecordRequest`.

### F04. 일정 수정·취소와 기록 확정 흐름 보완

**현재:** 경기 생성·조회·투표·기록 API는 있지만 일정·장소·마감 수정 및 취소 API는 확인되지 않는다. `CANCELED` 표시와 통계 제외는 구현되어 있다. 기록 저장은 경기 시작 전인지 검사하지 않고 `COMPLETED`로 전환한다. 목록은 경기 시각이 지나면 기록 여부와 무관하게 ‘매치 종료’로 표시한다.

`updateHistoricalMatchParticipants()`는 경기 시각과 운영진 권한을 검사하지만 취소 상태는 검사하지 않는다. 취소 기능을 추가할 때 기존 참가 명단 수정 경로도 같은 상태 정책에 포함해야 한다.

**제안:** 운영진이 일시·장소·마감을 수정하고 취소 사유를 남길 수 있게 한다. 시간 변경 시 기존 투표를 유지할지 재확인할지 선택할 수 있어야 한다. 기록은 ‘기록 대기’와 ‘확정’을 구분하고, 미래 경기 확정은 차단하거나 별도의 명시적 예외 흐름으로 제한한다.

**완료 기준:** 취소된 경기에서 투표·포메이션 편집이 차단되고 통계에서 제외된다. 일정 연기 후 마감과 투표 상태가 일관된다. 미래 경기의 실수 저장으로 투표가 잠기지 않는다. 과거 경기 등록은 기존 전용 흐름을 유지한다.

### F05. 출석률·투표 응답률·실제 출석률의 의미 구분

**현재 반영 상태:** 종료되었거나 양 팀 점수가 기록된 경기의 투표 후 불참은 출석 횟수에서 제외한다. 분모는 해당 선수가 참가 명단에 포함된 경기 수다. 훈련에도 같은 규칙을 적용한다. 이 수정은 유지한다.

**남은 정책:** 예정 경기의 참석 투표는 여전히 출석에 포함되고, 불참 또는 미투표 상태로 실제 출전한 선수는 현재 출석 분자에 포함되지 않는다. 따라서 현 지표는 투표와 실제 기록을 조합한 값이다. 또한 통계의 개인 기록 합계와 순위의 집계 대상 경기 선택 로직이 각각 구현되어 있다.

예를 들어 한 선수의 대상이 ‘종료 경기 실제 참석 1회 + 예정 경기 참석 투표 1회’이면 현재는 2/2회다. ‘종료 경기 불참 투표 후 실제 출전 1회’만 있으면 현재는 0/1회다. 이는 현재 수식의 설명이며, 예정 경기를 빼거나 실제 출전만 집계하도록 변경하려면 별도의 정책 결정이 필요하다.

**제안:** 현 지표의 이름·도움말을 유지·명확화하면서 필요 시 ‘확정 경기 실제 출석률’을 추가한다. 응답률이 필요하면 `(참석 응답+불참 응답)/응답 대상`이라는 별도 지표로 제공한다. 경기·훈련 구분과 공통 집계 조건을 한곳에서 정의한다. 실제 출석 확정 여부가 필요하면 기본값 `false`와 미확인 상태를 구분할 방법도 검토한다.

**완료 기준:** 예정 참석, 실제 불참, 투표 없이 출전, 기록 미확인, 취소, 명단 미포함 사례별 기대값이 문서와 테스트에 있다. 통계 수치를 누르면 그 값을 구성한 경기를 확인할 수 있다. 이미 추가된 `TeamAttendanceStatisticsTest`도 CI에 포함한다.

근거: [MatchService.kt](../be/src/main/kotlin/com/yonghoo/team_manager/match/service/MatchService.kt)의 `getAttendanceStatistics`, `getPlayerRankings`; [통계 화면](../fe/src/app/team/[teamId]/statistics/page.tsx); [출석률 테스트](../be/src/test/kotlin/com/yonghoo/team_manager/match/service/TeamAttendanceStatisticsTest.kt).

### F06. 과거 팀원 기록과 회비 대상 기간

**현재:** 통계·순위·회비의 표시 대상은 현재 `ACTIVE` 팀원 목록이다. 내보내기는 상태를 `LEFT`로 바꾸며 과거 참가 기록 자체를 삭제하지는 않는다. 회비는 기록 없는 달을 모두 `UNPAID`로 표시하고 가입 시점에 따른 대상 월 구분은 없다.

**영향:** 팀원을 내보내면 이전 시즌 통계와 회비 화면에서 그 선수의 행이 사라진다. 연중 가입자의 가입 전 월도 미납으로 보인다. 데이터 삭제와 화면 조회 제외는 구분해야 한다.

**제안:** ‘현재 팀원’과 ‘기간 내 활동한 전체 선수’ 조회 옵션을 제공한다. 회비는 납부 의무 시작·종료 월을 정하고 ‘대상 아님’을 미납·면제와 구분한다. 재가입이 있다면 현재 상태 하나로 과거 소속 기간을 추정하지 않는다.

**완료 기준:** 탈퇴 전 경기·납부 기록이 운영진의 과거 조회에서 남는다. 7월 가입자의 1~6월이 자동 미납으로 표시되지 않는다. 일반 팀원의 과거 타인 정보 조회 범위는 별도 권한 기준을 따른다.

근거: [TeamRepository.kt](../be/src/main/kotlin/com/yonghoo/team_manager/team/repository/TeamRepository.kt)의 `selectMembersByTeamId`; [TeamService.kt](../be/src/main/kotlin/com/yonghoo/team_manager/team/service/TeamService.kt)의 `removeTeamMember`; [FeePaymentService.kt](../be/src/main/kotlin/com/yonghoo/team_manager/fee/service/FeePaymentService.kt).

### F10. 과거 명단을 수정할 때 기존 참가자와 기록 보존

**현재:** 과거 명단 편집 화면은 기존 참가 상태를 읽지만, 저장 본문은 현재 활성 팀원인 `members`에서만 만든다. 서버의 `validateHistoricalMatchParticipants()`도 현재 활성 팀원 ID만 허용한다. 따라서 예전에 출전한 뒤 내보낸 선수는 일반적인 재저장에서 빠질 수 있고, 클라이언트만 고쳐 그 ID를 보내도 서버 검증에 걸린다.

명단 교체는 요청에 없는 참가 기록에 `deletedAt`을 설정한다. 이때 참가자에 기록된 골·어시스트 등은 이후 집계 대상에서 제외되지만, `matches.teamScore`와 미지정 득점은 재계산하지 않는다. 화면이 다음 기록 페이지로 이동하더라도 그 페이지에서 다시 저장하기 전까지 불일치가 남는다. 또한 기존 `PENDING/INVITED`를 편집 화면 초기화 시 `AVAILABLE`로 변환하므로 명단 정정 과정에서 원래 미응답 상태가 참석으로 바뀔 수 있다.

**영향:** 참가자 A가 2골, B가 1골을 기록한 3:0 경기에서 A를 명단에서 제외하면 표시 점수는 3:0인데 활성 선수의 골 합계는 1이 된다. 내보낸 선수는 운영진이 제외 의사를 표시하지 않아도 같은 경로를 탈 수 있다. 이는 F06의 조회 범위 문제와 달리 참가 기록의 활성 여부까지 바꾸는 저장 문제다.

**제안:** 기존 참가자는 현재 소속 상태와 관계없이 편집·저장에서 유지하고, 새로 추가할 선수의 자격 검증과 구분한다. 기록이 있는 참가자 제거는 영향 안내 후 명시적으로 처리한다. 실제 경기 점수와 개인 득점의 정정 정책을 정해 제거 차단, 별도 보관, 미지정 득점 전환 등 합의된 방식으로 한 트랜잭션에서 일관성을 보장한다. 미응답 투표도 사용자가 정정하지 않으면 그대로 유지한다.

**완료 기준:** 내보낸 선수가 포함된 과거 명단을 변경 없이 저장해도 참가자·골·출석·포메이션 자격이 바뀌지 않는다. 득점자 제거 시 점수와 개인 기록의 관계가 깨지지 않고 변경 이력이 남는다. 취소 경기에서의 편집 여부는 F04와 동일하게 적용한다.

근거: [과거 명단 편집 화면](../fe/src/app/team/[teamId]/match/history/page.tsx)의 `loadTeam`, `handleSubmit`; [MatchService.kt](../be/src/main/kotlin/com/yonghoo/team_manager/match/service/MatchService.kt)의 `updateHistoricalMatchParticipants`, `validateHistoricalMatchParticipants`; [MatchParticipantRepository.kt](../be/src/main/kotlin/com/yonghoo/team_manager/match/repository/MatchParticipantRepository.kt)의 `replaceHistoricalParticipants`; [MatchResponse.kt](../be/src/main/kotlin/com/yonghoo/team_manager/match/dto/MatchResponse.kt).

### F11. 삭제된 팀의 경기 API 접근 조건 일치

**2026-10-23 점검 당시:** 팀 삭제는 팀을 `INACTIVE`로 바꾸고 `deletedAt`을 설정한다. 마지막 팀장의 팀원 기록과 경기 기록은 그대로 남는다. 팀·통계·포메이션 조회는 팀 상태를 검사하지만, `MatchService.getMatchAndValidateViewPermission()`은 경기 존재와 활성 팀원 여부만 검사한다. 이때 팀원 검사도 부모 팀 상태를 읽지 않는다.

**영향:** 삭제 전 마지막 팀장의 유효한 로그인 상태에서 기존 경기 ID로 직접 요청하면 경기 상세·참가 명단·메모 및 일부 쓰기 경로가 부모 팀 삭제를 감지하지 못한다. 프런트의 팀 조회가 404를 표시하더라도 서버 API에 같은 검사가 필요하다. 타인의 계정이나 다른 팀 권한으로 접근 가능하다는 주장은 아니다.

**제안:** 경기 권한의 공통 진입점에서 팀의 활성·미삭제 상태도 검증한다. 과거 데이터는 보존하되 삭제된 팀의 하위 리소스 접근 정책을 팀·경기·포메이션에 동일하게 적용한다.

**완료 기준:** 마지막 팀장이 팀을 삭제한 뒤 기존 경기의 조회·메모·기록·투표·과거 명단 수정 API를 직접 호출해도 404로 거절한다. 활성 팀의 정상 경기 접근은 유지한다. FE 가드를 거치지 않는 API 회귀 테스트로 검증한다.

## 5. 구조·운영 측면의 보완

### T01. 여러 운영진의 동시 수정과 변경 이력

**확인한 구조:** 포메이션은 버전 검사를 하고, 경기 참가 쓰기는 경기 잠금을 사용한다. 반면 회비 upsert는 먼저 조회한 뒤 없으면 생성하며 별도의 부모 행 잠금이 없다. 역할 변경은 현재 팀장을 읽은 뒤 역할을 순차 갱신한다. 경기 기록은 잠금은 있지만 요청에 읽었던 버전을 전달하지 않아 오래된 화면의 저장을 구분할 수 없다.

**검증할 위험:** 같은 월 회비의 동시 최초 저장으로 중복 행 생성, 서로 다른 대상에 대한 동시 팀장 위임, 먼저 저장한 기록을 오래된 화면이 덮어쓰기. 시즌 기본값·가입 승인도 같은 방식으로 동시 요청을 점검한다. 이 항목들은 코드 경로에 기반한 위험이며 운영 환경 재현 결과는 없다.

**제안:** 팀·경기 등 이미 존재하는 부모 행을 정해 일정한 순서로 잠그고, 편집에는 버전 검사를 적용한다. 새 UNIQUE·외래키·CHECK 제약을 추가하지 않는 저장소 지침을 따른다. 회비·기록·역할 변경에는 변경자·시각·변경 전후 값을 남긴다. 기존 팀 정보 변경 이력은 있으므로 이를 없애거나 중복 구현하지 않는다.

**완료 기준:** 동시에 두 요청을 보내도 회비 행이 하나이며 팀장 역할의 불변식이 유지된다. 오래된 기록 저장은 충돌을 알려주고 입력을 보존한다. 실제 DB와 같은 MySQL 계열의 트랜잭션 동작으로 검증한다.

### T02. 테스트 누락 방지와 배포 후 확인

**현재:** 배포 워크플로는 수동 실행이며 `bootJar`와 프런트 빌드를 수행한다. 테스트·lint를 실행하는 PR 워크플로는 저장소에서 확인되지 않는다. 프런트 `npm test`는 `tests/*.test.mjs`만 대상으로 하므로 `src/features/match/model/notes.test.mjs`는 기본 명령에서 빠진다. 배포는 프로세스 종료 후 `nohup`으로 시작하며 실제 HTTP 정상 응답 확인 단계가 없다.

**제안:** PR에서 FE 테스트·lint·타입검사·빌드, BE 테스트를 실행한다. 테스트 파일의 검색 경로를 일원화하고 DB가 필요한 테스트 환경도 분리한다. 배포 후 제한 시간 안에 FE·BE의 정상 응답을 확인하고 실패 시 이전 빌드로 복구한다. 서버 프로세스 재시작 관리는 서비스 관리자로 옮기는 방안을 검토한다.

### T03. 조회 비용과 큰 서비스·화면 정리

**현재:** 경기 목록은 팀의 전체 경기와 참가자를 가져온다. 출석 통계는 전체 경기를 읽어 기간 필터링·집계·정렬 후 페이지를 자른다. 경기 참가자 조회는 선수마다 팀원 정보를 한 번씩 읽는다. 화면 권한 검사와 본문이 같은 팀·경기를 다시 조회하며, 통계 화면은 기간·정렬·페이지 변경 때 팀 정보와 시즌도 다시 요청한다. `MatchService`에는 일정·기록·투표·통계·순위·메모가 함께 있다.

**제안:** 먼저 쿼리 수·응답 크기·지연을 측정한다. 기간 조건을 DB로 내리고 참가자·팀원 정보를 일괄 조회한다. 통계는 전체 대상 선수의 집계·정렬 후 페이지를 나눠야 하며, 선수 목록을 먼저 잘라 집계하면 전체 출석률순 정렬이 깨진다. FE는 팀 문맥과 시즌을 공유하고 최신 요청의 응답만 반영한다. `MatchStatisticsService`, 기록 전용 서비스와 화면별 데이터 훅으로 책임을 나누되 지금 단계에서 서비스 분리나 새 상태 관리 라이브러리를 전제로 하지 않는다.

**완료 기준:** 팀원이 늘어도 참가자 조회 쿼리가 선수 수만큼 증가하지 않는다. 페이지 이동 때 불필요한 팀·시즌 재요청이 없다. 빠르게 기간을 바꿔도 이전 응답이 현재 통계를 덮어쓰지 않는다. 최적화 전후 집계 결과는 같다.

### T04. 스키마·복구·개발 문서의 현재 상태 정리

**확인 사항:** 신규 스키마, 누적 변경 SQL, 과거 별도 migration 파일이 함께 있다. `schema.sql`에는 `match_records`가 있지만 현재 Kotlin 코드에서 해당 테이블 사용은 확인되지 않는다. 루트 README는 한 줄이고 FE README는 기본 생성 안내다. 포메이션 문서는 아직 ‘구현 미착수’·8개 프리셋으로 적혀 있어 현재 9개 프리셋과 맞지 않는다.

신규 UNIQUE 제약을 추가하지 않는 지침과 별개로, 현재 `schema.sql`에는 사용자 아이디·이메일 UNIQUE 제약이 이미 있다. 이를 정비 과정에서 일괄 제거하라는 뜻은 아니다. 실제 DB 상태와 기존 가입 경로의 의존성을 먼저 확인해야 한다.

**제안:** 신규 설치와 기존 DB 갱신의 적용 순서·적용 이력·배포 전 확인 절차를 문서화한다. 현재 지침대로 기존 DB 변경은 `change_schema.sql` 끝에 추가하고 전체 파일을 재실행하지 않는다. 미사용 추정 테이블은 운영 데이터·외부 사용처를 확인한 뒤 정리 여부를 결정한다. 포메이션 문서의 구현 상태와 프리셋을 갱신하고, 개발 실행·환경변수 이름·테스트 명령을 README에 정리한다.

**복구 보완:** 로고 문서에 이미 있는 DB·로고 폴더 백업 지침을 실제 복원 확인 절차로 연결한다. 배포 디렉터리 외부 저장 경로와 로그 보존을 확인한다. 저장소만으로 실제 백업이 없다고 단정하지 않는다.

**완료 기준:** 새 DB와 기존 DB를 갱신한 결과가 현재 ORM과 일치한다. 비밀 값 없이 새 개발자가 실행할 수 있다. 백업에서 팀·경기·회비와 로고를 함께 복원하는 절차를 검증한다.

근거: [schema.sql](../be/src/main/resources/schema.sql), [change_schema.sql](../be/src/main/resources/change_schema.sql), [BE 지침](../be/AGENTS.md), [루트 README](../README.md), [FE README](../fe/README.md), [포메이션 문서](match-formations.md), [팀 로고 문서](team-logos.md).

### T05. 계정 복구 전에 서버 세션 폐기 기준 마련

**현재:** 로그아웃은 응답에서 access·refresh 쿠키를 만료시킨다. refresh는 JWT 검증 후 사용자 존재를 확인해 access 토큰만 새로 발급한다. 토큰·스키마에서 세션 ID, 폐기 목록, 사용자별 토큰 버전은 확인되지 않는다. 따라서 현재 브라우저의 쿠키 제거는 제공하지만 기존 토큰을 서버 차원에서 폐기하는 기능은 없다.

**제안:** N06의 비밀번호 복구·변경을 도입하기 전에 ‘현재 기기 로그아웃’과 ‘모든 기기 로그아웃’ 범위를 정한다. 서버에서 폐기 가능한 세션 또는 사용자 토큰 버전을 도입하고, access와 refresh 양쪽의 효력 종료 기준을 맞춘다. refresh 회전을 도입한다면 FE의 동시 401 요청도 하나의 갱신 요청을 공유하도록 처리한다.

**완료 기준:** 비밀번호 변경 또는 전체 로그아웃 후 기존 세션의 재발급이 거절된다. 현재 기기만 로그아웃하는 동작이 다른 기기를 의도치 않게 종료하지 않는다. 여러 API의 동시 만료 복구가 불필요한 로그아웃으로 이어지지 않는다. 현재 방식만으로 침해가 발생했다고 단정하지 않는다.

근거: [UserController.kt](../be/src/main/kotlin/com/yonghoo/team_manager/user/controller/UserController.kt)의 `signOut`, `refreshAccessToken`; [UserService.kt](../be/src/main/kotlin/com/yonghoo/team_manager/user/service/UserService.kt)의 `refreshAccessToken`; [JwtTokenProvider.kt](../be/src/main/kotlin/com/yonghoo/team_manager/user/auth/JwtTokenProvider.kt); [HTTP 클라이언트](../fe/src/shared/api/http.ts)의 `fetchWithAccessRefresh`.
