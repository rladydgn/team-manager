# Team Manager 개선 작업 계획

작성일: 2026-10-23 · 갱신일: 2026-10-28 · 상태: F11·F10-a·F10-b 보존 처리·F03 완료, F01 사용자 요청으로 제거, F02 구현·로컬 검증 완료(MySQL 미검증), T04-a 문서 일부 완료, 배포 관련 변경·CI 구축 제외

기준: [프로젝트 점검과 기능 개선 제안](project-review-and-roadmap.md)의 2026-10-23 재검토본. 원문의 F01~F11, T01~T05, N01~N09 **25개 제안 ID를 유지**한다. `-a`, `-b`는 같은 제안을 나눈 실행 단위다.

CI 구축·PR 자동 검증 구성은 2026-10-27 사용자 요청으로 작업 범위에서 제외했다. 기능 구현에 필요한 로컬 검증은 유지한다.

2026-10-28 사용자 요청으로 **배포 관련 변경은 진행하지 않는다.** T02와 T04-b의 운영 적용·백업 설정·복구 작업은 현재 범위에서 보류한다. 개발 안내와 현행 기능 문서 정리는 T04-a의 독립 범위로 진행한다.

이 문서는 후속 구현을 위한 작업 목록이다. 문서 작성 요청이 모든 제안의 구현·정책 확정·운영 배포를 뜻하지 않는다. 구현 요청이 들어오면 지정된 범위부터 진행하고, 아래 순서는 범위를 정할 때 사용하는 권장 순서로 활용한다. 코드 근거와 현재 문제의 상세 설명은 원문을 함께 읽는다.

## 1. 작업 중 질문하고 결정을 기록하는 규칙

사용자 요청: **“결정이 필요한 내용들도 적어줘. 그리고 작업 진행할 때 물어보도록 해.”**

1. 작업에 착수하면 관련 코드, 기존 사용자 답변, 이 문서의 결정 상태를 먼저 확인한다. 이미 결정된 내용은 다시 묻지 않는다.
2. 아래 `D-...` 결정이 미확정이면 **그 결정에 의존하는 API·화면·DB 변경 전에 사용자에게 질문한다.** 코드 조사와 재현, 영향 분석을 먼저 해서 실제 선택지와 영향을 설명할 수 있는 상태로 질문한다.
3. 한 번에 현재 작업에 필요한 질문만 1~3개씩 묻는다. 각 질문에는 선택지, 권장안, 기존 데이터·사용 흐름에 미치는 영향을 붙인다. 이 문서의 권장안은 사용자 답변을 대신하지 않는다.
4. 답변이 없으면 해당 결정에 의존하는 구현은 진행하지 않는다. 시간 경과를 동의로 해석하지 않는다. 조사·검증이나 정책과 무관하게 진행 가능한 다른 실행 단위는 계속할 수 있다.
5. 답변을 받으면 5절의 상태를 `확정` 또는 `부분 확정`으로 바꾸고 7절에 결정 내용·답변 날짜·적용 범위를 기록한다. 일부만 답변했다면 나머지는 계속 미결정으로 둔다.
6. 구현 도중 새로운 정책 문제가 발견되면 결정 ID를 추가하고 같은 방식으로 질문한다. 기존 결정의 변경이 필요할 때도 영향부터 설명한다.
7. 단순 코드 구조·파일 배치·동일 동작을 보장하는 수정은 작업자가 판단한다. 별도 정책이 없는 항목마다 형식적인 재승인을 요청하지 않는다.

예: F10의 기존 참가자·투표 보존은 F10-a로 다룬다. 기록이 있는 선수를 **명시적으로 삭제했을 때** 점수를 어떻게 처리할지는 F10-b 착수 시 D-F10을 질문한다. 회비나 알림 정책을 이때 미리 한꺼번에 묻지 않는다.

이 규칙은 [루트 작업 지침](../AGENTS.md)에서도 참조한다. 구현 시 [BE 지침](../be/AGENTS.md), [FE 지침](../fe/AGENTS.md), 화면 변경 시 [디자인 가이드](design-system.md)를 함께 따른다. 이 작업 계획만으로 별도의 SDD 문서 생성을 시작하지 않는다.

## 2. 유지할 기존 동작과 공통 완료 조건

다음은 이미 반영된 요구사항이므로 이번 개선에서 유지한다.

- 생성한 포메이션은 상단 탭으로 선택하며, `4-1-2-3`을 포함한 기존 9개 프리셋·10개 제한·편 구분·버전 충돌 처리를 유지한다.
- 경기 참여 팀원은 참여 우선·이름순으로 정렬한다. 열 이름은 **주포지션**, 등번호도 함께 표시한다. 포메이션 후보에도 두 정보를 유지한다.
- 기록된 경기에서 투표 후 실제 불참한 사람을 출석 횟수에서 제외하는 기존 수정은 되돌리지 않는다. 예정 경기·실제 출석 지표의 추가 변경은 D-F05로 따로 결정한다.
- 인증·권한은 서버에서 검증한다. FE 화면 접근 차단만으로 API 권한 검사를 대신하지 않는다.
- 기존 참가·개인 기록·회비·소속 이력을 일괄 삭제하거나 추정으로 덮어쓰지 않는다. 기존 데이터 전환이 필요한 작업은 대상 조회, 전환 규칙, 복구 방법을 먼저 준비한다.
- 신규 UNIQUE·FK·CHECK 제약을 추가하지 않는 BE 지침을 따른다. 기존 제약을 일괄 제거하지 않는다. 기존 DB용 DDL은 `change_schema.sql` 끝에 추가하고, 이미 적용한 문장을 포함해 전체 파일을 다시 실행하지 않는다.

각 실행 단위는 다음을 만족해야 완료로 기록한다.

- [ ] 관련 결정이 확정되었거나, 미결정 내용과 무관한 범위임을 기록했다.
- [ ] API 입력·응답·권한·오류·상태 전이와 기존 데이터 영향이 정리되었다.
- [ ] 변경한 핵심 동작의 회귀 검증을 실행했고 결과를 남겼다. 미실행 검증은 이유와 남은 범위를 적었다.
- [ ] UI가 바뀌면 모바일 375px·데스크톱 1440px에서 핵심 흐름을 확인했다.
- [ ] 스키마가 바뀌면 신규 설치·기존 DB 갱신 경로와 복구 가능성을 확인했다.
- [ ] 실제 완료한 실행 단위만 체크하고, 전체 제안의 나머지 작업을 완료로 표시하지 않았다.

## 4. 실행 단위별 작업과 인수 기준

### F11. 삭제 팀의 하위 경기 접근 차단

- [x] 경기의 공통 권한 진입점에서 부모 팀의 활성·미삭제 상태를 확인하고, 이를 거치지 않는 경기 API도 조사한다.
- [x] 조회·참가 명단·메모·투표·편 배정·포메이션·기록·과거 명단 수정에 동일한 조건을 적용한다. 저장 데이터는 보존한다.
- **완료:** 마지막 팀장이 팀을 삭제한 뒤 유효한 인증으로 기존 경기 API를 직접 호출하면 404다. 활성 팀의 정상 접근과 기존 역할 제한은 유지된다.
- **질문:** 추가 제품 결정 없음. 현재 팀 접근 정책과 동일하게 맞추는 범위다.
- **접점:** [MatchService](../be/src/main/kotlin/com/yonghoo/team_manager/match/service/MatchService.kt), [TeamRepository](../be/src/main/kotlin/com/yonghoo/team_manager/team/repository/TeamRepository.kt), [MatchFormationRepository](../be/src/main/kotlin/com/yonghoo/team_manager/match/repository/MatchFormationRepository.kt).

### F10. 과거 명단과 개인 기록 보존

- [x] **F10-a:** 기존 참가자와 새로 추가 가능한 활성 팀원을 구분해 조회·표시한다. 기존 참가자는 현재 LEFT 상태여도 요청에서 누락하지 않는다. 서버도 기존 참가자의 유지와 신규 추가 자격을 구분한다.
- [x] **F10-a:** PENDING·INVITED를 AVAILABLE로 자동 변환하지 않는다. 아무 변경 없이 저장했을 때 참가 상태·개인 기록·합계·기존 배치가 달라지지 않도록 회귀 사례를 고정한다.
- [x] **F10-b 보존:** 확정된 D-F10에 따라 현재 팀원 명단에 없는 기존 참가자 및 실제 출석·지각·골·도움·클린시트 기록이 있는 참가자의 명단 제외를 화면·서버에서 차단한다. 전체 선택 해제도 보존 대상을 유지하며 기존 투표·개인 기록·점수·포메이션을 바꾸지 않는다.
- [ ] **F10 변경 이력(T01 연계):** 명시적 경기 기록 정정·허용된 명단 변경의 감사 이력은 T01-c에서 범위·조회 권한을 결정한 뒤 구현한다. 이번 보존 처리에 새 이력 저장·조회 기능은 포함하지 않았다.
- **보존 완료 기준:** A 2골·B 1골의 3:0 경기에서 A가 LEFT가 되어도 명단 재저장으로 A가 사라지지 않는다. A 또는 출석·개인 기록이 있는 선수를 누락한 요청은 저장 전에 거절해 원래 점수·기록·배치를 보존한다.
- **진행 결과(2026-10-27):** F10-a 및 사용자 결정에 따른 F10-b 보존 처리 완료. 실제 팀 탈퇴 후에도 기존 참가자·투표·개인 기록·점수·포메이션이 남고, 보호 대상의 명단 제외 요청이 부분 저장 없이 거부됨을 검증했다. 별도 기록 정정·명단 변경 감사 이력은 T01 연계 대기다.
- **결정:** D-F10은 2026-10-27 기록 보존으로 확정했다. 별도 기록 정정·감사 이력 정책은 D-F03·D-F04-b·D-T01에 해당하며 해당 실행 단위 착수 시 질문한다.
- **접점:** [과거 명단 화면](../fe/src/app/team/[teamId]/match/history/page.tsx), [MatchService](../be/src/main/kotlin/com/yonghoo/team_manager/match/service/MatchService.kt), [MatchParticipantRepository](../be/src/main/kotlin/com/yonghoo/team_manager/match/repository/MatchParticipantRepository.kt).

### F03. 실제 출석과 기록의 모순 차단

- [x] 불참+양수 골·도움·클린시트 및 불참+지각의 서버 검증을 통일한다.

- **접점:** [TeamRepository](../be/src/main/kotlin/com/yonghoo/team_manager/team/repository/TeamRepository.kt), [FeePaymentService](../be/src/main/kotlin/com/yonghoo/team_manager/fee/service/FeePaymentService.kt).

### F09. 문의 답변

- [ ] 팀 운영진과 구분되는 서비스 운영자 권한·부여 절차, 문의 관리 목록·답변 저장 API를 구현한다.
- [ ] 답변 본문·답변자·시각·수정 이력과 ANSWERED 전환을 같은 트랜잭션으로 저장한다. 작성자 화면에 답변을 표시한다.
- **완료:** 답변은 지정된 서비스 운영자만 작성하며, 문의 작성자와 권한 있는 서비스 운영자만 내용을 조회한다. 팀장이라는 이유만으로 타인의 문의를 볼 수 없다. 저장 실패 시 완료 상태만 남지 않는다.
- **질문 시점:** 운영자 권한과 답변 모델 설계 전 D-F09.
- **접점:** [문의 기능 문서](inquiries.md), [InquiryController](../be/src/main/kotlin/com/yonghoo/team_manager/inquiry/controller/InquiryController.kt), [InquiriesTable](../be/src/main/kotlin/com/yonghoo/team_manager/inquiry/domain/InquiriesTable.kt).

### N05. 회비 금액·납부일·내보내기

- [ ] F06-b의 대상 월에 청구액·납부액·납부일을 연결하고 부분 납부·면제·부상 처리와 잔액 계산을 적용한다.
- [ ] 월별 회비 기준을 보존해 현재 금액 변경이 과거 청구를 바꾸지 않게 한다. 기존 상태만 있는 자료의 금액은 임의 추정하지 않는다.
- [ ] 운영진의 월 합계·변경 이력·CSV 내보내기를 제공하고 서버 권한·대상 기간·출력 값의 안전한 처리를 확인한다.
- **완료:** 납부 대상·상태·금액·월 합계가 일치한다. 동시 저장이 중복 납부를 만들지 않는다. 내보낸 자료가 선택 기간과 일치한다.
- **질문 시점:** 금액·납부 데이터 모델과 과거 자료 전환 전 D-N05.
- **접점:** [회비 화면](../fe/src/app/team/[teamId]/fee-payment/page.tsx), [TeamFeePaymentsTable](../be/src/main/kotlin/com/yonghoo/team_manager/fee/domain/TeamFeePaymentsTable.kt).

### T05. 서버 세션 폐기

- [ ] 현재 기기·모든 기기 로그아웃과 비밀번호 변경 시 세션 종료 범위를 확정한 뒤 세션 저장 또는 버전 방식을 선택한다.
- [ ] access·refresh 검증에서 폐기 상태를 적용하고 기존 토큰의 전환 방법을 정한다. refresh 회전을 도입하면 FE 동시 401 요청이 갱신을 공유하게 한다.
- **완료:** 폐기된 세션은 새 access를 발급받지 못하며, 기존 access의 유효 기간도 합의와 일치한다. 현재 기기 종료가 다른 기기까지 의도치 않게 종료하지 않는다.
- **질문 시점:** 세션 모델·기존 로그인 전환 설계 전 D-T05. N06-a 구현 전에 끝낸다.
- **접점:** [UserService](../be/src/main/kotlin/com/yonghoo/team_manager/user/service/UserService.kt), [JwtTokenProvider](../be/src/main/kotlin/com/yonghoo/team_manager/user/auth/JwtTokenProvider.kt), [HTTP 클라이언트](../fe/src/shared/api/http.ts).

### N06. 계정 복구·변경과 본인 팀 탈퇴

- [ ] **N06-a:** 본인 확인, 일회성·만료 복구 토큰, 비밀번호 변경, 재사용 차단과 T05의 세션 폐기를 연결한다. 일반 계정과 카카오 계정의 가능한 동작을 구분한다.
- [ ] **N06-b:** 본인 팀 탈퇴 API·화면을 추가한다. 팀장의 위임, 마지막 팀원의 기존 팀 삭제 흐름, F06의 과거 기록·회비 처리 기준을 연결한다.
- **완료:** 만료·재사용 복구 요청은 실패한다. 비밀번호 변경 후 기존 세션은 정책대로 종료된다. 본인 탈퇴가 팀장 공백이나 과거 기록 삭제를 만들지 않는다.
- **질문 시점:** N06-a 전 D-N06-a, N06-b 전 D-N06-b. 두 작업은 별개로 선택할 수 있다.
- **접점:** [UserController](../be/src/main/kotlin/com/yonghoo/team_manager/user/controller/UserController.kt), [UserService](../be/src/main/kotlin/com/yonghoo/team_manager/user/service/UserService.kt), [TeamService](../be/src/main/kotlin/com/yonghoo/team_manager/team/service/TeamService.kt).

### T03. 조회 성능과 화면 데이터 흐름

- [ ] 팀원·경기 수가 다른 테스트 데이터에서 쿼리 수·응답 크기·시간·중복 요청 수를 먼저 측정하고 비교 기준을 기록한다.
- [ ] 기간 필터·일괄 참가자/팀원 조회를 적용한다. 통계는 **전체 대상 집계·정렬 후 페이지 처리**를 유지한다.
- [ ] 팀·시즌 데이터 재사용과 이전 요청 응답 무시를 적용하고, 필요한 범위에서 통계·기록 서비스 및 화면 데이터 처리를 분리한다.
- **완료:** 최적화 전후 집계 결과·정렬이 같고 참가자 조회 쿼리가 선수 수만큼 증가하지 않는다. 빠른 기간 변경에도 이전 응답이 덮어쓰지 않는다. 개선 수치는 실제 측정값으로 남긴다.
- **질문:** 현재 결과·최신 응답을 유지하는 범위는 추가 결정 없음. 캐시로 최신성 보장을 바꾸거나 새 인프라가 필요하면 별도 결정 ID를 추가한다.
- **접점:** [MatchRepository](../be/src/main/kotlin/com/yonghoo/team_manager/match/repository/MatchRepository.kt), [통계 화면](../fe/src/app/team/[teamId]/statistics/page.tsx), [PageAccessBoundary](../fe/src/features/auth/ui/PageAccessBoundary.tsx).

### N03. 반복 일정·검색·달력

- [ ] 기간·시즌·훈련·진행 상태 검색부터 구현하고, 선택한 범위에 따라 달력과 반복 생성을 추가한다.
- [ ] 반복 회차 식별·중복 생성 방지와 한 회차/이후 회차 변경·취소 범위를 F04 상태 정책에 연결한다. 일정 파일 제공은 별도 실행 단위로 둔다.
- **완료:** 같은 생성 요청을 다시 보내도 중복 일정이 생기지 않는다. 개별 일정 수정이 의도치 않게 전체 일정을 바꾸지 않는다.
- **질문 시점:** 반복 규칙·달력 범위 설계 전 D-N03.
- **접점:** [경기 목록](../fe/src/app/team/[teamId]/match/page.tsx), [MatchService](../be/src/main/kotlin/com/yonghoo/team_manager/match/service/MatchService.kt).

### N04. 경기·회비 알림

- [ ] 선택한 사건·수신자·시점을 기준으로 앱 내 알림·읽음 상태를 구현한다. 생성 중복과 재시도를 구분할 수 있는 사건 식별을 마련한다.
- [ ] 일정 변경·취소·납부 완료 시 이미 예약된 알림을 정리한다. 외부 채널이 선택되면 수신 설정·실패 재시도·발송 이력을 추가한다.
- **완료:** 동일 사건의 재처리로 중복 알림이 생기지 않는다. 취소 경기나 납부 대상이 아닌 달의 독촉이 발송되지 않는다.
- **질문 시점:** 알림 대상·시간·채널 설계 전 D-N04. 외부 실제 발송은 별도 범위를 명시한다.
- **접점:** 경기·회비 서비스의 변경 사건, 팀 화면의 새 알림 진입점. F04·F06 및 도입한 N05 기준을 재사용한다.

### N07. 선수별 상세 기록

- [ ] 선수 행에서 기간·시즌을 유지한 상세 화면으로 연결한다. 경기별 출석·골·도움과 추이를 같은 집계 기준으로 제공한다.
- [ ] F05의 수치별 경기 조회를 재사용하고 F06의 과거 팀원 공개 범위를 적용한다.
- **완료:** 통계 표 합계와 상세 합계가 일치하며, 기간·훈련·자체 경기 선택을 바꿔도 기준이 같다.
- **질문 시점:** 노출 지표·조회 권한·첫 화면 범위 전 D-N07.
- **접점:** [통계 화면](../fe/src/app/team/[teamId]/statistics/page.tsx), [MatchService](../be/src/main/kotlin/com/yonghoo/team_manager/match/service/MatchService.kt).

### N08. 쿼터 계획·교체·실제 출전

- [ ] 첫 범위를 계획된 쿼터 비교와 실제 출전 기록 중에서 결정한다. 계획을 도입하면 포메이션과 쿼터 관계를 별도로 표현한다.
- [ ] 실제 출전을 도입하면 쿼터 길이·교체·중복 시간·편 변경과 개인 기록 연결을 검증한다.
- **완료:** 포메이션 배치만으로 실제 출석·출전 시간이 확정되지 않는다. 계획 비교와 실제 기록의 숫자를 구분해 표시한다.
- **질문 시점:** 쿼터·시간 모델 설계 전 D-N08. F02·F03·F05 기준을 먼저 확정한다.
- **접점:** [FormationPages](../fe/src/features/match/ui/FormationPages.tsx), [기록 화면](../fe/src/app/match/[matchId]/record/page.tsx).

### N09. 포메이션 이미지 저장

- [ ] 현재 포메이션을 이미지로 저장하고 이름·등번호 포함 여부와 이미지 범위를 선택하게 한다.
- [ ] 모바일 다운로드, 한글 글꼴, 긴 선수명·빈 자리·편 표시를 확인한다. 공개 링크는 이미지 저장과 별도 범위로 둔다.
- **완료:** 선택한 포메이션과 표시 옵션이 결과 이미지와 일치한다. 공개 링크를 도입하는 경우에만 만료·철회·조회 범위를 추가 결정한다.
- **질문 시점:** 이미지에 포함할 정보·포맷·범위 전 D-N09.
- **접점:** [FormationPages](../fe/src/features/match/ui/FormationPages.tsx), [디자인 가이드](design-system.md).

## 7. 결정·작업 기록 양식

2절의 기존 요구사항과 결정표에서 확정된 D-F10 기록 보존 정책을 적용한다. 나머지 미결정 정책은 해당 작업 전에 질문한다.

```text
작업 ID / 실행 단위:
진행 상태 / 작업일:
구현 요청 범위:
결정 ID / 상태(확정·부분 확정·미결정):
사용자 답변 날짜와 내용:
적용 범위 / 남은 질문:
변경한 API·화면·데이터:
기존 데이터 처리 / 복구 방법(해당 시):
실행한 검증과 결과:
미실행 검증과 이유:
완료한 실행 단위 / 다음 작업:
```

일부 작업이나 테스트만 끝났다면 그 범위만 기록한다. 제안서의 우선순위·코드 근거가 달라지는 변경은 [개선 제안 문서](project-review-and-roadmap.md)에도 함께 반영한다.
