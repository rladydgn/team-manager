# Team Manager 디자인 가이드

이 문서는 새 화면 개발과 기존 화면 수정 시 따르는 UI·UX 기준입니다. 구현 기준은 `fe/src/app/globals.css`의 토큰과 공통 UI이며, 디자인을 변경하면 이 문서도 함께 수정합니다.

## 1. 디자인 방향

- **간결한 팀 운영 도구.** 실제 팀·경기·기록을 우선하고, 예시 데이터를 실제 현황처럼 표시하지 않습니다.
- **차분한 색상과 명확한 위계.** 밝은 중립 배경, 흰 표면, 인디고 강조색을 사용합니다. 주요 행동과 선택 상태에 색을 집중합니다.
- **화면당 하나의 제목, 하나의 주요 행동.** 제목 아래 설명은 필요한 경우 한두 문장만 둡니다.
- **정보는 한 번만.** 팀 소개·팀원 수·이용 안내를 여러 카드에 반복하지 않습니다.
- **같은 작업은 같은 위치와 문구.** 등록은 상단 우측 또는 폼 하단, 목록 필터는 제목 아래, 파괴적 작업은 일반 작업과 떨어뜨려 배치합니다.

참고한 방향: [Linear의 2026 UI refresh](https://linear.app/changelog/2026-03-12-ui-refresh)의 정보 위계·밀도 정리와 [NN/g의 미니멀 디자인 원칙](https://www.nngroup.com/articles/aesthetic-minimalist-design/). 특정 서비스의 화면을 그대로 복제하지 않습니다.

## 2. 색상: 값 대신 의미를 사용

새 화면은 `bg-brand`, `text-muted`, `border-line`처럼 Tailwind 토큰을 사용합니다. 같은 의미의 색을 새 hex 값으로 만들지 않습니다.

| 토큰 | 값 | 용도 |
| --- | --- | --- |
| `canvas` | `#f7f8fa` | 앱 배경 |
| `surface` / `white` | `#ffffff` | 카드·폼·메뉴 |
| `subtle` | `#f2f4f7` | 표 헤더·보조 배경 |
| `line` | `#e5e8ed` | 카드 테두리·구분선 |
| `line-strong` | `#d4dae3` | 입력창·보조 버튼 |
| `ink` | `#202938` | 제목·주요 본문 |
| `secondary` | `#525f70` | 보조 본문 |
| `muted` | `#647084` | 설명·메타 정보 |
| `placeholder` | `#8b96a6` | 입력 예시·장식 아이콘 |
| `brand` | `#4f6f9f` | 주요 버튼·강조 |
| `brand-hover` | `#405f8d` | 주요 버튼 hover |
| `brand-ink` | `#36557f` | 선택 항목·강조 텍스트 |
| `brand-soft` | `#edf2f9` | 선택 항목 배경 |
| `brand-ring` | `#dce5f2` | 포커스 주변 강조 |
| `danger` | `#b42332` | 오류·삭제 |
| `success` | `#277052` | 성공·완료 |

`danger-soft`, `danger-line`, `success-soft`, `success-line`을 상태 배경과 테두리에 사용합니다. 카카오 등 외부 서비스의 브랜드색과 기존 통계 항목 구분색은 목적이 명확한 예외입니다. 상태는 색뿐 아니라 ‘답변 대기’, ‘답변 완료’처럼 텍스트로도 표시합니다.

## 3. 타이포그래피와 간격

- OS 기본 글꼴과 한국어 시스템 글꼴을 사용합니다. 외부 폰트 로딩에 의존하지 않습니다.
- 본문은 `text-sm`(14px), 긴 안내문은 `leading-6` 또는 `leading-7`입니다.
- 페이지 제목은 `page-title`: 모바일 24px, 데스크톱 30px, `font-semibold`입니다. 홈의 소개 제목만 더 크게 쓸 수 있습니다.
- 섹션 제목은 16~20px, 메타 정보는 12px입니다. 모든 텍스트를 굵게 만들지 않습니다.
- 기본 간격은 4px 배수입니다. 관련 요소는 8~12px, 카드 내부는 20~28px, 섹션 사이에는 24~32px 정도를 둡니다.
- 주요 콘텐츠 폭은 `max-w-6xl`입니다. 가이드·문의는 `max-w-4xl`, 인증 폼은 `max-w-md`로 읽는 폭을 제한합니다.

## 4. 공통 구현

| 요소 | 구현 위치 | 사용 기준 |
| --- | --- | --- |
| 테마·공통 클래스 | `fe/src/app/globals.css` | 토큰과 공통 스타일의 기준 |
| 페이지 제목 | `fe/src/shared/ui/PageHeading.tsx` | 제목·설명·문맥·주요 행동 |
| 선형 아이콘 | `fe/src/shared/ui/Icon.tsx` | 동일한 viewBox·선 굵기, 기본 16px |
| 상단 탐색 | `fe/src/shared/ui/AppHeader.tsx` | 64px 높이와 하단 1px 선 유지 |
| 팀 내 탐색 | `fe/src/features/team/ui/TeamDetailTabs.tsx` | 권한별 탭, 모바일 줄바꿈 |
| 공통 404 | `fe/src/shared/ui/NotFoundPage.tsx` | 존재하지 않거나 접근할 수 없는 페이지 |
| 훈련 표시 | `fe/src/features/match/ui/MatchTrainingBadge.tsx` | 경기 목록·상세에서 훈련 진행 시에만 표시 |
| 문의 상태 | `fe/src/features/inquiry/ui/InquiryPresentation.tsx` | 답변 대기·답변 완료 배지 |

### 페이지 구조 예시

```tsx
import Link from "next/link";
import { Icon } from "@/shared/ui/Icon";
import { PageHeading } from "@/shared/ui/PageHeading";

<main className="flex-1 bg-canvas">
  <div className="page-shell">
    <PageHeading
      label={team.name}
      title="경기 일정"
      description="경기 일정을 확인하고 참석 여부를 알려주세요."
      action={canManage ? (
        <Link href={`/team/${team.id}/match/new`} className="btn-primary">
          <Icon name="plus" /> 경기 등록
        </Link>
      ) : undefined}
    />
    <section className="surface-card p-5 sm:p-6">…</section>
  </div>
</main>
```

### 버튼과 폼

- `btn-primary`: 현재 화면의 주요 행동. 인디고 배경과 흰 글자.
- `btn-secondary`: 취소·목록·보조 행동. 흰 배경과 얇은 테두리.
- `btn-quiet`: 덜 중요한 이동·보조 행동.
- 기본 버튼은 최소 44px 높이, 모서리는 8px입니다. 탐색 항목은 40px, 촘촘한 표 안의 컨트롤은 별도 크기를 허용합니다.
- 이동은 `Link`/`a`, 저장·상태 변경은 `button`을 사용합니다. 아이콘만 있는 버튼에는 `aria-label`을 붙입니다.
- 입력은 `field`를 우선 사용합니다. 모든 필드에 보이는 레이블을 둡니다. placeholder로 레이블을 대체하지 않습니다.
- 모바일 입력 글자는 16px로 유지해 입력 시 과도한 확대를 방지합니다.
- 필수 정보부터 보여주고, 선택 정보가 많으면 ‘추가 정보 · 선택’으로 접습니다.
- 처리 중에는 버튼을 비활성화하고 ‘저장 중…’처럼 현재 행동을 표시합니다. 오류가 나면 작성 내용을 유지합니다.

### 카드·표·배지

- 주요 카드에는 `surface-card`(16px 모서리, 얇은 테두리, 작은 그림자)를 사용합니다. 촘촘한 데이터 영역은 `rounded-xl`(12px)만 사용해도 됩니다.
- 서로 붙은 목록이나 표에는 각 행마다 카드를 만들지 않고 구분선을 사용합니다.
- 강한 그림자와 여러 겹의 테두리를 겹치지 않습니다. 떠 있는 메뉴는 `shadow-popover`로 구분합니다.
- 숫자 열은 정렬을 맞추고, 날짜와 수치 형식을 통일합니다. 테이블의 의미 있는 `th`와 `scope`를 유지합니다.
- 회비 표의 월 헤더는 상단 앱 헤더 아래 `top-[calc(4rem+1px)]`에 고정합니다. 이를 감싸는 요소를 스크롤 컨테이너로 바꾸면 고정이 깨질 수 있으므로 함께 확인합니다.

## 5. 탐색·권한·상태

- 상단 ‘팀 홈’은 선택한 팀, ‘팀 목록’은 전체 팀으로 이동합니다. 같은 이름으로 두 목적지를 표시하지 않습니다.
- 팀원에게 필요한 탭만 표시합니다. 비로그인·비팀원에게는 팀 홈만 표시하고 운영진 탭은 일반 팀원에게 숨깁니다.
- 메뉴를 숨기는 것은 서버 권한 검사를 대체하지 않습니다. [접근 제어 기준](access-control.md)을 함께 확인합니다.
- 로딩·빈 목록·검색 결과 없음·오류는 서로 다른 상태입니다. 실패를 ‘자료 없음’으로 표시하지 않습니다.
- 오류에는 다시 시도를 제공하고, 비어 있는 화면에는 가능한 다음 행동을 알려줍니다.
- 훈련은 `isTraining`이 참인 경우에만 ‘훈련 진행’ 배지를 표시합니다. 미진행 배지나 문구는 만들지 않습니다.
- 통계의 전체 경기 수와 경기 출석에는 훈련을 포함하고, 훈련 수·출석은 추가로 표시합니다. 요약은 ‘기간 내 전체 경기 10회 · 훈련 3회’ 형태로 씁니다. 순위도 훈련 기록을 포함하되, 종료됐거나 점수가 기록된 경기만 집계합니다. 취소된 경기는 통계와 순위에서 제외합니다.
- 계정 메뉴는 바깥 클릭과 Escape로 닫히며, Escape 후 열기 버튼으로 포커스가 돌아갑니다.
- 로고는 기존 `fe/public/team-manager-logo.png`를 사용합니다. 상단 로고의 `unoptimized`는 로컬 최적화 요청 정체를 피하기 위한 설정입니다. 이를 변경하면 실제 이미지 표시를 확인합니다.

## 6. 반응형·접근성

- 375px 모바일과 1440px 데스크톱에서 우선 확인하고, 상단 메뉴는 320px에서도 겹치지 않게 합니다.
- 모바일은 세로 흐름, 큰 화면은 관련 정보끼리 그리드로 배치합니다. 긴 팀 이름과 사용자 이름에도 대응합니다.
- 팀 탭은 모바일에서 줄바꿈합니다. 일반 화면 전체에 가로 스크롤이 생기지 않게 합니다.
- 데이터 표는 기존 모바일 카드·목록 표현을 유지합니다. 모든 정보를 억지로 한 줄에 넣지 않습니다.
- 키보드 포커스 표시, 본문 바로가기, 레이블, 처리 상태를 유지합니다. 새 상호작용은 키보드로도 사용할 수 있어야 합니다.
- 중요한 일반 텍스트는 배경과 4.5:1 이상의 대비를 목표로 합니다. `placeholder`는 중요한 설명 문구에 쓰지 않습니다.
- 모션은 짧은 색상 전환 정도로 제한하고 `prefers-reduced-motion`을 존중합니다.

## 7. 문구 원칙

| 구분 | 기준 |
| --- | --- |
| 사람 | 팀장 / 부팀장 / 팀원 / 용병 |
| 팀의 권한 있는 역할 | 운영진 |
| 서비스 문의 담당 | 서비스 운영자 |
| 경기 | ‘매치’ 대신 ‘경기’ |
| 기존 기록과 회원 연결 | 기존 기록 연결 / 계정 연결 |
| 페이지 제목 | 팀원, 경기 일정, 회비 납부, 내 문의처럼 짧은 명사 |
| 행동 | 경기 등록, 저장, 가입 신청, 문의 보내기처럼 결과가 드러나는 표현 |
| 설명 | ‘확인할 수 있습니다’의 반복을 줄이고 ‘확인하세요’ 등 간결한 표현 |
| 완료·오류 | 무엇이 완료됐거나 실패했는지, 다음에 무엇을 할 수 있는지 설명 |

‘화면’, ‘폼’, ‘카테고리’, 영어 대문자 장식 제목 등 구현 중심 표현을 줄입니다. 예: ‘생성 폼 닫기’ → ‘닫기’, ‘카테고리’ → ‘문의 유형’. 실제로 보장하지 않는 무료·실시간·자동 처리 같은 표현을 추가하지 않습니다.

## 8. 이후 작업에서 확인할 것

1. 먼저 기존 화면과 이 문서에서 같은 패턴을 찾습니다.
2. 새 색상·버튼 스타일을 만들기 전에 공통 토큰과 클래스를 재사용합니다.
3. 권한, 데이터 로딩, 에러 처리와 같은 기존 동작을 유지합니다.
4. 변경한 화면을 모바일·데스크톱에서 확인하고 `npm run lint`, `npm run build`를 실행합니다.
5. 테스트는 권한 등 중요한 동작을 바꿨을 때 필요한 것만 짧게 작성합니다. 단순 스타일·문구 변경마다 테스트를 추가하지 않습니다.
6. 공통 기준을 바꾼 경우 구현과 이 문서를 함께 갱신합니다.
